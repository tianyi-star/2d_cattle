# Evidence audit — what this repository actually supports

Scope: commit `104b5b6` ("Delete results/rank_curves.md") on `main`, plus full git history
(`git log --all`, 66 commits, 20 remote branches).
Purpose: establish, before any prose is written, exactly which datasets, backbones, losses,
training settings and numbers exist in this repository, so that a manuscript submitted to
*Computers and Electronics in Agriculture* (CEA) contains no fabricated result.

Target-journal note: this audit was begun for *计算机工程与应用* (JCEA) and re-targeted to
*Computers and Electronics in Agriculture* (Elsevier, ISSN 0168-1699). Section 9 records what
CEA's format requires and what our evidence is missing for it; §9.1 is the requirement-by-
requirement table. The audit content itself is journal-independent: the same evidence base
supports or fails to support a submission to either venue.

## 1. Headline finding (read this first)

**The repository contains no measured recognition result of any kind.**

Every file under `results/` is a hand-written placeholder generated by
`src/metrics.py` / `src/results.py` from hard-coded dictionaries. The generating code says so
explicitly, in its own docstrings and in the `kind` field it writes:

| File | `kind` field | Generator statement |
| --- | --- | --- |
| `results/metrics.json` | `metrics_placeholder` | `src/metrics.py:1-8` — "All numbers are *placeholders for drafting*. They are not measurements from the private UAV archive." |
| `results/accuracy_curves.json` | `accuracy_curves` | `src/metrics.py` `build_acc_curves()` returns `kind: "simulated_accuracy_curves"` |

Three consequences:

1. **No number in `results/` may appear in the manuscript as a result.** The values 0.861,
   0.878, 0.996, 0.847, 0.806, 0.862, 0.828, 0.835 and all per-epoch curves are invented
   constants. `src/results.py:20-38` names its own dictionary `_FINAL`, with a comment
   describing the "scenario": *"only Yaowu Wang + sam sits at the 0.995 anchor … every other
   cell stays in the 0.800-0.900 band"*. That is a narrative target, not a measurement.
2. **The placeholder disclaimer was deliberately erased from the committed artefacts.**
   Commits `2e1e2d4`, `cdde8cc`, `ddaf922`, `6cbb367`, `fc1314c` changed the visible footnotes
   from *"Simulated … Not measured. Replace with a real training log after a server run."* to
   the bare label *"Accuracy / Recall@1 / Recall@5 / mAP."*, and renamed the files
   `simulated_metrics.*` → `metrics.*` and `simulated_accuracy_curves.*` →
   `accuracy_curves.*`. The `kind` string was rewritten from
   `simulated_metrics_placeholder` to `metrics_placeholder`. In other words the files were
   dressed to look measured while the underlying constants were unchanged
   (`0.847/0.861/0.891/0.876` etc. are identical before and after the rename). **A manuscript
   built on these files would misrepresent invented data as experimental data.**
3. **`git log --all` contains no real run artefact.** No `outputs/` path, no
   `summary_six_cells.json`, no `outputs/*/metrics.json` and no `rank_callback.json` was ever
   committed. `.gitignore` excludes `outputs/`, `data/`, `*.pt`, `*.pth`, so the measured files
   would be invisible even if they existed locally. `README.md` states measured summaries "land in
   `outputs/summary_six_cells.json`" — that file has never existed in this repository.

4. **Both headline mechanisms were broken in the audited revision and are now fixed.** At
   `104b5b6` the SAM arm wrote the same rectangle as the box arm (§3) and the pruning operator
   removed nothing (§4), so neither the $\Delta_{\mathrm{SAM}}$ contrast nor the compression claim
   was testable. Commit `ac69fb7` (`fix/sam-and-pruning`) fixes both; §3.1 and §4.1 give the
   verified current behaviour. **What has not changed is that no recognition result has been
   measured** — the machinery now exists, the experiment does not.

## 3. The SAM masking stage: was a stub, now implemented

**Status: fixed in `fix/sam-and-pruning` (commit `ac69fb7`).** The finding below is kept as the
record of what the audited `main` revision contained; the current state is stated at the end of
this section.

`README.md` and `paper/method.tex` describe a two-arm crop protocol whose entire scientific
contrast is SAM-masked back-pattern crops ($I_{\mathrm{sam}}$) versus YOLO box crops
($I_{\mathrm{box}}$). At commit `104b5b6` the code could not produce $I_{\mathrm{sam}}$.

`src/preprocess.py:165-168` at that revision:

```python
if crop == CROP_SAM and sam_weights:
    # Without a GPU SAM runtime in every environment, keep the box crop
    # but mark the arm; servers with SAM can replace this branch.
    pass
```

Inside the `crop == CROP_SAM` branch, the code did nothing and then wrote `crop_img`, which is the
plain rectangle. So the `sam` arm and the `bbox` arm produced **byte-identical crops** whenever the
detector path was used. `sam_weights` was never loaded; `ultralytics` was the only model dependency
actually imported. There was no SAM implementation and no $\operatorname{Crop}(I \odot M, B_M)$
anywhere in the tree.

The only way to obtain a "SAM" manifest at that revision was `--ready-dir`, which ingested a folder
of already-background-removed images supplied by the user. No such folder was in the repository.

### 3.1 Current state after the fix

`src/sam_mask.py` (604 lines) now implements the stage, and `src/preprocess.py` calls it for
`--crop sam`. Verified by reading the code and running its tests (13 SAM tests pass on CPU with no
weights required; the opt-in real-checkpoint test is skipped by default):

| Property | Implementation |
| --- | --- |
| Prompt | detector box only; returns mask $M$; writes $\operatorname{Crop}(I \odot M, B_M)$ |
| Backends | `segment_anything` (`vit_h`/`vit_l`/`vit_b`), `mobile_sam` (`vit_t`), `ultralytics` |
| Default | `model_type="vit_b"`, `backend="auto"` (`src/sam_mask.py:221`; `configs/path.yaml`) |
| Loading | lazy — a bbox-only run never allocates a segmenter |
| Cache | on disk, keyed by image id + detection box + segmenter fingerprint; `CACHE_SCHEMA = "sam-mask-v1"` |
| Refinement | clip to box → largest connected component → hole fill → reject below `min_area_frac` (default 0.005) |
| Missing weights | `SamWeightsMissing` raised; preprocessing aborts before writing any crop or manifest |
| Config | `--sam-model-type/--sam-backend/--sam-device/--sam-cache-dir`; `sam_cache_dir: data/sam_mask_cache` |

The failure mode this fixes is subtle and worth naming: the old `pass` branch meant a researcher
could run the "SAM ablation" to completion, see two columns of numbers, and never learn that both
columns came from identical pixels. The new code removes the silent fallback deliberately — a
missing checkpoint raises instead of degrading.

**What is still true:** no $\Delta_{\mathrm{SAM}}$ has been *measured* on real data. The code can
now produce both arms; no run on the archive exists.

## 4. Structured pruning: was inert, now physically removes units

**Status: fixed in `fix/sam-and-pruning` (commit `ac69fb7`).** The finding below is the record of
the audited `main` revision.

At commit `104b5b6`, `README.md` and `paper/method.tex` presented `pruned_vit_arcface` as the
proposed contribution: task-specific structured pruning of attention heads and MLP channels with
subsequent fine-tuning.

I instantiated the model from the repository's own code and config
(`configs/experiment.yaml`, `vit_prune_ratio: 0.25`, `vit_name: vit_tiny_patch16_224`) and
measured:

```
vit_tiny num_heads = 3  ->  int(3 * 0.25) = 0   # n_drop == 0, head pruning skipped entirely
mlp hidden      = 768  ->  int(768 * 0.25) = 192 # intended
MLP rows actually zeroed by `w[idx].zero_()`: 0 of 192
tensors changed by _prune_vit(0.25) from an identical init: 0
parameters, pruned vs unpruned: 5,623,232 vs 5,623,232
```

Two independent defects:

* **Head pruning was a no-op at ratio 0.25** — `vit_tiny_patch16_224` has 3 heads, and
  `int(3 × 0.25) = 0`.
* **MLP pruning was a silent no-op at any ratio** — the code wrote
  `mlp.fc1.weight[drop_idx].zero_()`. Advanced indexing returns a *copy*, so the in-place write
  never reached the parameter. Verified directly: 0 of 192 intended rows were zeroed.

So `pruned_vit_arcface` was, at that revision, architecturally identical to an unpruned ViT-Tiny.

### 4.1 Current state after the fix

Re-measured independently on `fix/sam-and-pruning`, by instantiating both variants and calling the
repository's own `count_parameters` and `estimate_flops` at 224 × 224:

| Variant | Parameters | MACs | Heads | MLP channels |
| --- | ---: | ---: | ---: | ---: |
| ViT-Tiny, unpruned (ρ = 0) | 5,623,232 | 1,074,757,632 | 36 | 9,216 |
| ViT-Tiny, pruned (ρ = 0.25) | **4,144,064** | **784,269,312** | 24 | 6,912 |
| Delta | −1,479,168 (−26.3 %) | −290,488,320 (−27.0 %) | −12 | −2,304 |

`units_to_prune` now applies half-up rounding with a floor of one unit, so `3 × 0.25` removes 1
head rather than 0; the tensors are rebuilt without the dropped rows and columns, so
`count_parameters` genuinely falls; and a request that would remove nothing raises rather than
training an unpruned model under a pruned name. 12 pruning tests pass, including one that pins the
old advanced-indexing no-op as a regression.

### 4.2 The criterion discrepancy — resolved in the text, code unchanged on purpose

**The implementation ranks by weight magnitude** (`_magnitude_scores` =
`weight.abs().mean(dim=1)`; the prune report literally records
`"criterion": "weight_magnitude"`). A discriminability-ratio criterion
$I(u)=\Delta(\phi)-\Delta(\phi^{(-u)})$ with
$\Delta = S_{\mathrm{inter}}/(S_{\mathrm{intra}}+\varepsilon)$ on a calibration split is a
different method with a materially higher cost: it needs a calibration split and one forward pass
per candidate unit.

Both write-ups now describe magnitude ranking as the implemented rule and present the $\Delta$
criterion only as an explicitly labelled design direction that was **not evaluated**:
`paper/manuscript-cea.md` §3.8 and §5.4, and `paper/method.tex` §`sec:pruning`. No result in the
repository was produced with the $\Delta$ criterion, and neither document claims otherwise. The
historical note survives as a comment above `_magnitude_scores` in `src/models.py`; the
`TODO(paper-alignment)` marker is gone because there is no longer a misalignment to track.

## 8. Identity-disjoint splitting: was specified in the paper, not implemented — now implemented

**Status: fixed.** The finding below is kept as the record of the audited `main` revision; §8.1
states the current behaviour and the command that reproduces it.

### 8.0 The finding at the audited revision

The manuscript specifies, and argues for, a partition in which each of the 96 animals appears in
exactly one of the training, validation and test sets. **At that revision the code did not do this.**
It did the opposite, and the consequence is that every rank-1 number the then-current pipeline could
produce was inflated.

`src/data.py:84-129` (`build_split_rows`), which `src/aggregate.py:51` (`build_seed_manifest`)
delegates to, iterates over identities and, for each one, shuffles *that identity's own images* and
deals them into `train` / `gallery` / `query` at a 0.6 / 0.2 / 0.2 ratio. Its docstring says so
plainly: *"Assign each image to train / gallery / query while keeping all identities."* Three
consequences:

1. **Identity leakage.** Every identity appears in all three splits. A model can reach high rank-1
   by recognising animals it was trained on, which is not identification.
2. **Near-duplicate leakage.** Consecutive UAV frames of one animal are nearly identical. Splitting
   within an identity puts temporally adjacent frames on both sides of the train/test boundary, so
   even the retrieval metric measures frame memorisation.
3. **No validation split existed at all.** `SPLITS = ("train", "gallery", "query")`
   (`src/data.py:18`); there was no `val`, no identity-holdout flag, and no code path that could
   produce one. (Fixed: `SPLITS` now includes `val`, and §8.1 describes the partition.)

Note also that `gallery` is not a held-out class set: `src/evaluate.py:154-159` ranks each query
against *individual gallery embeddings* with duplicate-identity suppression, so gallery images of a
trained animal are simply more training-distribution views of it.

**Required before any reported figure:** a partitioning routine that assigns identity ids to
`train` / `val` / `test` disjointly, emits the three lists, and asserts that their intersection is
empty. The manuscript's §3.2.1 specifies the protocol.

### 8.1 Current state after the fix

`src/data.py` now implements the protocol, and it is the default:

| Property | Implementation |
| --- | --- |
| Default mode | `build_split(..., split_mode="identity")`; `build_seed_manifest()` and the `manifest` CLI subcommand both default to it |
| Assignment | identity ids sorted, shuffled with `random.Random(seed)`, then consumed in order: test takes the first identity ids with at least `min_test_images` images, then validation, then training |
| Disjointness | `assert_identity_disjoint()` raises `IdentityLeakageError` naming the identity and both partitions; `src/train.py` and `src/evaluate.py` call it before use |
| Partitions | `train`, `val`, `test`; gallery and query are both drawn from the held-out test animals only |
| Proportions | `--train-frac / --val-frac / --test-frac`, defaults 0.6667 / 0.1667 / 0.1667 → **64 / 16 / 16 identities** for the 96-identity archive, allocated by largest remainder |
| Test eligibility | `--min-test-images` (default 2) keeps single-frame animals out of test, because they cannot supply both a gallery and a query view |
| Checkpoint selection | `src/train.py` ranks validation queries against validation galleries; the test gallery/query pair is only read by `src/evaluate.py` after training |
| Legacy mode | `split_mode="within"` (CLI `--split-mode within`) restores the old per-identity shuffle; it is never a default, and both its JSON record and Markdown summary state that any Rank-1 from it is inflated |
| Record | `manifest.csv` + `manifest.split.json` (mode, seed, proportions, identity lists, counts, per-identity statistics, totals, CSV SHA-256) + `manifest.table1.md` (Table 1, ready to paste) |

**Table 1 is generated from the manifest.** `manifest.table1.md` carries exactly the quantities
Table 1 of the manuscript asks for — identities per split, images per split, images per identity
min / median / max and mean ± SD, and the exclusion list — so the table is filled from the split
record rather than transcribed, and the numbers cannot drift from the split that was actually used.
The JSON records the same values in machine-readable form plus the CSV's SHA-256, which identifies
the exact split a reported figure was produced with.

Reproduce it on the machine that holds the archive:

```bash
# Plan only, no files written:
python3 -m src.aggregate manifest --image-root /path/to/identity_crops \
  --output-manifest data/manifest.csv --seed 0 --dry-run

# Write the split and its records:
python3 -m src.aggregate manifest --image-root /path/to/identity_crops \
  --output-manifest data/manifest.csv --seed 0
```

or, for all seeds and both crop arms plus a copy of the records in the results directory:

```bash
scripts/run_all_cells.sh --data-root /path/to/crop_trees --manifest-only
```

**What is still true:** no run has used the new partition yet, so no identity-disjoint Rank-1 has
been measured, and Table 1's identity and image counts cannot be filled from the repository — the
archive is on the author's GPU server and not reachable here. The proportions are known
(64 / 16 / 16 identities); the image counts and per-identity statistics come from the manifest the
first run writes, not from this audit.


## 9. Settings that are documented and can be reported as *design*, not as outcome

From `configs/experiment.yaml` (paper config):

```
seed 0 · image_size 224 · batch_size 8 · epochs 30 · learning_rate 1e-4
weight_decay 1e-4 · num_workers 2 · embedding_dim 512 · eval_every 5
arcface_scale 64.0 · arcface_margin 0.5
yolo_backbone csp_small · vit_name vit_tiny_patch16_224 · vit_prune_ratio 0.25
wang_backbone resnet50
```

Augmentation (`src/data.py:132-150`): resize to 224², random horizontal flip, colour jitter
(0.15/0.15/0.1), ImageNet normalisation. Optimiser: Adam (`src/train.py:93`), not SGD.
No LR schedule, no warm-up, no early stopping, no mixed precision, no EMA.

**`epochs: 30` directly contradicts the placeholder curves**, which are drawn at
`eval_every: 200` over epochs 200/400/600/800/1000 (`src/results.py:41`, `src/metrics.py:44`).
The committed "training curves" therefore describe a 1000-epoch schedule on a config that
trains for 30. A further self-inconsistency proving the curves are fabricated.

Also absent at the audited revision: any validation split. `SPLITS = ("train", "gallery",
"query")` had no `val`, while `paper/method.tex` builds its whole F-ODS argument on a validation
split. **Fixed for the split itself** (§8.1): `SPLITS` now contains `val`, and `src/train.py` selects
its checkpoint on the validation animals rather than on the test animals. F-ODS itself is still not
implemented, so the F-ODS narrative in `paper/method.tex` remains unsupported by code.
